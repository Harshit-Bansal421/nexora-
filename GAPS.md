## Backend-dependent behavior

- The earlier `GET /api/v1/posts/:post_id` 500 was a backend bug, not malformed seed data: `returnDocument` was incorrectly present as an aggregation stage, and `ownerInfo` had already been unwound. The approved two-line fix was applied only in `src/controllers/post.controller.js`. Retesting now returns HTTP 200 for a seeded post, an older post, and the newly created diagnostic post; a fake ID returns 404.
- For an older orphaned community (`69e52385564580c589fe0540`), an unauthenticated `GET /api/v1/pages/:page_id` currently returns HTTP 200 with `owner: null`. In the authenticated code path, `src/controllers/page.controller.js:783` dereferences `page.owner._id`, which previously produced `TypeError: Cannot read properties of null (reading '_id')`. This is an orphaned-reference condition exposing a backend null-guard bug. Suggested fix: explicitly handle a missing populated owner before dereferencing it (for example, return a controlled 404). The record was not edited or deleted.
- The backend omits member totals for users who cannot access the member roster, and the member-list endpoint is permission-gated. The frontend reports an unavailable count rather than showing an invented number.
- Public post and community pages were initializing authenticated Socket.IO connections even for logged-out visitors. The frontend now gates room joins on `isAuthenticated` in `PostCommentsPage` and `PageViewPage`. The authenticated checks in this pass showed no Socket.IO handshake error.
- The hand-authored fixture was reseeded in the confirmed development database `Nexora`: 35 users, 8 pages, 120 posts, 405 comments, 3 join requests, and 46 notifications; no OTPs. It has 30 post images and 0 duplicate image URLs. The unseed pass removed only identifiable prior fixture records (35 users, 8 pages, 120 posts, 715 comments, 3 join requests, and 64 notifications); OTPs and unrelated records were left untouched.

## Local image support limitation

- The user model and post model store image values as strings, but backend upload/read paths use Cloudinary upload and `getOptimizedImage`; the backend app has no static-file middleware. A relative frontend asset path would therefore not be a supported persisted image URL under the current backend contract. The requested local image/avatar migration is blocked while backend source changes are disallowed. Existing external image URLs can also fail independently, as the `loremflickr.com` 500 demonstrated.
- Shared `Avatar` and `ImageWithFallback` components are now used for user avatars in navigation, post cards/details, comments, notifications, profiles, community rosters, and post composition, and for post/community images. Failed or missing sources render a neutral theme-based placeholder instead of a broken-image glyph or unrelated stock portrait. The frontend lint and production build pass after this change. This prevents broken layout but does not repair an external image host or upload the failed image elsewhere.
